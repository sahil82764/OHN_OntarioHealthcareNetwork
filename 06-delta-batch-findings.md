# Delta batch testing — results and findings

**Date:** 2026-09-01
**What was tested:** a full incremental pass through the medallion architecture (Bronze → Silver → Gold), driven by `data generator/deltaBatch.py --apply .` — a second, smaller batch layered on top of the original full load, deliberately engineered to exercise watermarks, SCD2 versioning, MPI (master patient index) stability, deduplication, and unknown-member resolution.

**Result: the medallion architecture works.** Every layer processed the delta end to end without failing, every fact table's Silver-to-Gold row count reconciled exactly, and the core design principles (never drop a row for a missing lookup, quarantine rather than corrupt, resolve identity once in Silver) held under real, messy incremental conditions. Four real defects were found in the process — documented below, deliberately left unfixed as portfolio/interview material rather than patched.

---

## What was confirmed working

- **Bronze reconciliation** — staging-to-Bronze row counts matched for every entity, every run.
- **REST API pagination + retry** — the hand-rolled paginated pull in `17_bronze_pull_api.ipynb` correctly walked all pages via keyset cursor (Fabric's native Copy activity couldn't — it buffers the whole response into one write, silently keeping only the last page).
- **MPI blocking** — three-key blocking cut 1.9 billion possible pairs down to ~97K–117K candidates, with a guard against pathological oversized blocks.
- **MPI match quality** (`21_mpi_accuracy_evaluation.ipynb`, against the synthetic `_truth` answer key): precision `0.9997`, recall `0.9116`, F1 `0.9536`, `88.97%` of real people reconstructed exactly, only `7` golden IDs spanning more than one real person out of `25,000`. The precision-over-recall tradeoff (auto-link threshold set above the F1-maximizing point) worked as designed — false merges are the clinical-safety risk, false splits are just inconvenient.
- **MPI review queue** — `63.2%` of false negatives were correctly routed to human review rather than confidently rejected; the algorithm mostly "knew what it didn't know."
- **SCD2 versioning** — `dim_bed` showed exactly `5` new versions against `bed_ward_change: 5` generated by the delta — an exact match confirming the mechanism works correctly when not compounded by other issues.
- **Silver quarantine** — `409` lab results (`result_ts` before `order_ts`) and `28` survey responses (score outside 1–10) correctly quarantined with reasons attached rather than corrupting downstream aggregates.
- **Full-snapshot entities working as designed** — `diagnosis`, `bed_assignment`, `billing_line`, `hospital`, `department`, `bed` all showed large Bronze "removed" counts in Silver's dedupe step; verified these are *intentional* daily full-snapshot accumulation (one partition per pipeline-run day), not bugs — each reconciled to exactly `original + delta` before dedup.

## Findings (confirmed, left unfixed by choice)

### 1. Watermark data loss — SQL Server incremental extraction

**What:** Seven append-mode SQL Server entities (`EHR.patient`, `EHR.admission`, `EHR.emergency_visit`, `FIN.invoice`, `FIN.patient_account`, `SCHED.patient`, `SCHED.appointment`) filter incremental extraction on `last_modified_ts > watermark_from`, with **no grace-period lookback**.

**Root cause:** `ctl.sp_get_entities_to_ingest` / `sp_batch_start` / `sp_commit_batch` (`00_control_framework.sql`) implement a plain business-timestamp watermark. Rows with a timestamp behind the stored watermark are silently and **permanently** dropped — the watermark only advances forward, so a future run never re-checks them.

**Evidence:** empirically confirmed on `EHR.admission` by querying SQL Server directly — the 1,045th-smallest `last_modified_ts` among 1,794 delta rows was `2026-08-08 19:19:12`, and exactly `750` rows above that boundary passed, matching the pipeline's actual committed count precisely. Same ~42–45% pass-through rate held across all seven entities. The watermark traces back to a real prior pipeline run (batch `SQLSRV_20260804054930` failed; a retry around `2026-08-08 19:19` succeeded and set the watermark the Sep 1 delta collided with).

**Why it happens:** the delta generator's 60-day window (July 3 – Sep 1) legitimately overlaps dates before the stored watermark. This is exactly the `late_arriving` scenario the delta generator was built to test — except it's not confined to the ~6% of rows deliberately flagged `late_arriving`; the whole window's overlap means ~55–58% of *all* new rows in these entities hit it.

**Fix (designed, not applied):**
1. Recovery: `ctl.sp_reset_watermark` for the affected entities forces a full reload; safe because Silver dedupes on `_row_hash`.
2. Prevention: add a grace-period lookback (`watermark_from - N days`) to the Copy activity's dynamic source query.

### 2. Medication order duplication — REST API extraction, same bug family, opposite direction

**What:** `lh_bronze.dbo.pharm_medication_order` contains `197,753` rows but only `100,242` distinct `medication_order_id`s — every one of the original `97,511` orders exists twice.

**Root cause:** two full pulls landed in Bronze under different batch IDs — `API_20260814125612...` (a real prior pipeline run) and `API_20260901202151...` (the Sep 1 delta run). Both pulled the **entire** dataset. `PHARM.medication_order` is registry-configured `load_type='incremental'`, `watermark_column='updated_at'`, and `api_server.py`'s `updated_since` filter (`r.get(ts_field) > normalised`) is structurally identical to the SQL watermark bug — but the Aug 14 run's Bronze write apparently succeeded while its watermark never advanced in `ctl.watermark`, so every subsequent run still sees a virgin watermark and re-pulls + re-appends everything.

**Same category as Finding 1, opposite failure mode:** instead of losing rows, this one duplicates an entire entity's history on every run, forever, until fixed.

**Impact:** Silver's `dedupe()` (partition by business key, order by `_ingest_ts` desc) absorbs this correctly — it does not propagate downstream. But it's a standing performance/storage tax: every future run reprocesses double the true data volume for this entity.

**Not fully confirmed:** the exact point of failure (`ctl.watermark` never written vs. `ctl.batch_log` stuck at `STAGED`) requires querying the Fabric Warehouse directly, which wasn't available in this session. Diagnostic queries:
```sql
SELECT * FROM ctl.watermark WHERE source_system = 'PHARM' AND entity_name = 'medication_order';
SELECT * FROM ctl.batch_log WHERE source_system = 'PHARM' AND entity_name = 'medication_order' ORDER BY start_ts;
```

### 3. Orphaned facts — quantified downstream consequence of Finding 1

**What:** `22 silver conform.ipynb`'s patient-resolution check, which showed `unresolved=0` for every entity at baseline, showed `378` orphaned fact rows post-delta:

| Entity | Unresolved |
|---|---|
| `silver_admission` | 29 |
| `silver_emergency_visit` | 31 |
| `silver_appointment` | 41 |
| `silver_medication_order` | 90 |
| `silver_billing_line` | 187 |

**Root cause:** these are fact records whose `patient_id` doesn't resolve in `silver_patient_xref` — direct evidence that a brand-new patient's own EHR/SCHED/FIN row was dropped by the watermark cutoff (Finding 1), while that same patient's admission/ED-visit/medication-order/billing-line record — a *different* table, a *different* independently-generated timestamp — happened to clear the bar and reach Bronze anyway.

**Value:** this is the cleanest, most concrete, precisely-quantified artifact of Finding 1's blast radius — not a theoretical concern, a specific number traced to a specific cause.

### 4. Gold SCD2 dating bug — new members born "today," not backdated

**What:** `40_Gold_Facts.ipynb`'s `lookup()` helper does a temporal join (`fact[event_ts] >= dim.effective_from_ts AND < dim.effective_to_ts`) for patient/doctor/department/hospital keys on time-sensitive facts. `30_Gold_Dim.ipynb`'s `scd2_merge()` only backdates `effective_from_ts` to `1900-01-01` on a dimension's **very first ever load**. Every subsequent incremental insert dates new members from `run_ts` — the exact instant the notebook executed.

**Consequence:** any fact for a newly-added dimension member with a historical event timestamp (virtually all of them — events are generated across a 60-day window, not at the precise second Gold happens to run) fails the temporal join and silently resolves to `UNKNOWN`, despite the member being correctly linked in Silver.

**Evidence:** confirmed via code, not just data. `29` of `fact_admission`'s `37` unresolved `patient_key` rows trace to Finding 3 (Silver-orphan patients); the remaining `~8` are patients that *did* survive the watermark but still got misdated in Gold.

**Why the observed impact is small:** this bug compounds with, and is partly masked by, Finding 1 — most potential victims never reach Bronze in the first place. It's a standing defect independent of the watermark bug, though, and will worsen over time as more incremental members get added on non-initial runs — unlike Finding 1, this one isn't specific to this delta's timing quirk.

**Same underlying pattern across all four findings:** control/audit metadata (a watermark, a batch commit status, a dimension's validity window) silently drifting out of sync with what actually landed in the data — manifesting as loss, duplication, orphaning, and misdating depending on which layer and which mechanism it hits.

## Optimization pointers

A few concrete opportunities surfaced while tracing this delta through the pipeline — not generic Spark tuning advice, specifically things observed in this run:

1. **Full-snapshot entities accumulate unbounded Bronze storage.** `diagnosis`, `bed_assignment`, `billing_line`, `hospital`, `department`, `bed`, `doctor`, `survey_response` all write one full-table partition *per day the pipeline runs*, by design (`13_bronze_commit_staging.ipynb`'s comment on this is explicit). There's no retention/vacuum policy visible anywhere in the notebooks — Bronze storage for these entities grows linearly with pipeline run frequency, not with actual data change volume. Worth adding a `VACUUM` policy or converting genuinely-incremental-capable entities (e.g., if `diagnosis` could get a real `modified_ts` column upstream) to true incremental extraction instead.

2. **Finding 2's duplication is also a performance problem, not just correctness.** Every future run against `pharm_medication_order` reprocesses double the true row count through Silver's dedupe step for no reason. Fixing the watermark issue would cut real, growing compute cost, not just clean up data.

3. **Silver's `dedupe()` cost grows with #1.** Since it windows over the *entire* accumulated Bronze history for full-snapshot entities (which keeps growing per point 1), this step gets progressively more expensive every single run, independent of how much data actually changed. This compounds with point 1 rather than being independent of it.

4. **MPI (`20_silver_patient_mdm.ipynb`) recomputes from scratch every run** — full blocking, scoring, and label-propagation clustering over the *entire* patient universe (`66,310` records this run, growing every delta), not just new/changed records. This is arguably the *correct* design choice (a new-records-only incremental match could miss cases like `surname_change` where an existing record needs re-evaluation against its own cluster), but it's a real, unbounded cost as the patient population grows. If MPI runtime becomes a bottleneck, consider a hybrid: incrementally match new records against existing clusters most runs, with a periodic full recompute (e.g., weekly) to catch cases the incremental pass would miss.

5. **No `OPTIMIZE`/`Z-ORDER` calls anywhere in the notebooks.** Standard Delta Lake table-layout maintenance (compaction, Z-ordering on frequently-filtered columns like `patient_golden_id`, `_batch_id`, `_load_date`) isn't present in any of the Bronze/Silver/Gold notebooks. Given how many joins key off `patient_golden_id`/`record_uid` throughout Silver and Gold, Z-ordering `silver_patient_xref` and `dim_patient` on their business keys would likely have a measurable, easily-demonstrable read-performance impact.

6. **What's already good, worth keeping:** MPI blocking (1.9B pairs → ~100K candidates) and the oversized-block guard are solid, appropriately-scoped optimizations already in place — no changes needed there.
